# 材料协同审核平台（Material Review Platform）

基于《材料协同审核平台 产品设计文档》实现的一套**多角色在线材料协同审核系统**，适用于需要“多人分工初审 + 管理员终审 + 结果邮件反馈”的审核场景（如报销材料、申报材料等）。

**核心流程**：针对一次特定事件，提交人上传本轮材料 → 双人随机初审（按派发时配置的期限执行，超时自动跳过）→ 管理员智能派发终审（按派发时持久化的期限执行，超时自动换人 + 双阈值兜底）→ 邮件反馈结果。本平台按一次性审核任务设计：同一轮每个团队原则上只提交一次；后续开展新的特定事件时，应重置数据库并重新开服。

**设计亮点**：
- 双盲独立初审，审核员互不可见、同团队自动回避（学工号优先、姓名兜底）；
- 双重排序分配算法实现负载均衡，超时人员自动降权；
- 终审环节提供“同人循环 ≥3 次 / 全局重分配 ≥5 次 / 交替循环检测”双阈值兜底，杜绝无限循环死锁；
- 全部写操作采用“Redis 分布式锁 + 乐观锁 + 行锁”三重并发保护。

## 1. 技术栈

| 层 | 技术 |
| :--- | :--- |
| 后端 | Python 3.12+ / FastAPI / SQLAlchemy 2.0 |
| 数据库 | PostgreSQL（推荐）或 SQLite（本地开发/测试） |
| 缓存与分布式锁 | Redis（`SET NX`，不可用时自动降级进程内锁） |
| 任务调度 | APScheduler（每 5 分钟超时扫描 + 邮件重试 + 每日衰减） |
| 前端 | Vue 3 + TypeScript + Vite + Element Plus + Pinia + Vue Router |
| 认证 | JWT（Bearer Token） + bcrypt 密码哈希 |

## 3. 快速开始

### 3.1 Docker 一键部署（推荐）

```bash
# 1. 复制环境变量并修改 SECRET_KEY / 超管密码 / SMTP
cp .env.example .env

# 2. 启动（自动建表 + 初始化超级管理员 + 启动前后端）
docker compose up -d --build

# 3. 访问
#    前端与后端同源: http://<服务器IP>:8000
```

首次登录超管账号会被强制修改密码；账号和密码应以 `.env` 中的 `SUPER_ADMIN_USERNAME` / `SUPER_ADMIN_PASSWORD` 为准（示例模板不提供可直接使用的真实密码）。使用本地命令行显式传入参数时，也可以使用 `python -m app.seed -u <用户名> -p '<密码>' --email <邮箱>`。

> 若仅用于本地体验，可不配置 SMTP；系统会把邮件标记为失败并进入重试队列，超管端显示黄色提示，不影响核心审核流程。

### 3.2 本地开发

后端：

```bash
cd backend
pip install -r requirements.txt

# 使用 PostgreSQL（推荐）：
#   docker run -d -p 5432:5432 -e POSTGRES_USER=review -e POSTGRES_PASSWORD=review -e POSTGRES_DB=review postgres:16
#   docker run -d -p 6379:6379 redis:7
export DATABASE_URL=postgresql+psycopg://review:review@localhost:5432/review
export REDIS_URL=redis://localhost:6379/0
export SMTP_HOST=... SMTP_USER=... SMTP_PASSWORD=...   # 可选，不配置则邮件发送失败自动进重试队列

# 不使用 PostgreSQL 时可用 SQLite 快速体验（无行锁，仅开发）：
#   export DATABASE_URL=sqlite:///./dev.db

python -m app.seed -u <用户名> -p '<强密码>' --email <邮箱>   # 建表 + 超管；也可使用环境变量 SUPER_ADMIN_*
uvicorn app.main:app --host 0.0.0.0 --port 8000
```

前端：

```bash
cd frontend
npm install
npm run dev        # http://localhost:5173 （/api 已代理到 8000）
```

## 4. 角色与登录

| 角色 | 登录后首页 | 权限 |
| :--- | :--- | :--- |
| 提交人（团队） | `/team` | 提交材料、进度看板、撤回、查看反馈 |
| 审核员 | `/staff` | 初审待办、通过/不通过、撤回重审（含补时逻辑） |
| 管理员 | `/admin` | 终审待办、初审意见墙、最终裁定 |
| 超级管理员 | `/super` | 用户管理、密码重置、工单干预、邮件日志、系统配置、负载监控、审计 |

**账号安全**：首次登录强制改密（密码≥8位且含大小写字母+数字+特殊字符）；连续 5 次登录失败锁定 30 分钟；超管敏感操作需二次输入自身密码确认。

**用户批量导入/导出（超管端）**：
- **导入**：超管在“用户管理”页下载 Excel 模板 → 按模板逐行填写（角色取值 `team/staff/admin/super_admin`；提交人须附成员姓名/学工号 JSON 数组）→ 上传导入，逐行校验并返回成功/失败明细（失败行不影响其他行）。
- **导出账密**：超管可一键导出全部用户账号与密码（.xlsx）。系统会保留最近一次由系统/超管设置（或用户自行修改）的密码明文（`users.plain_password`），供超管发放/恢复账号；导出操作记录审计日志，请妥善保管导出文件。

所有账号由超管在后台预置，不开放注册。

## 5. 核心业务规则速览

- **状态机**：`pending → first_reviewing → admin_reviewing → passed/rejected`；超管可将已通过工单打回为 `returned`，提交人修改后重新提交；提交人可在允许撤回的阶段撤回至 `withdrawn`，异常挂起至 `pending_admin_intervention`（提交人端显示“加急处理中”，撤回按钮隐藏且后端强制 403 拦截）。
- **提交限制**：本平台面向一次特定事件的一次性审核使用，同一轮中每个团队原则上只提交一次，不面向长期、反复提交场景设计；新的特定事件应在重置数据库并重新开服后使用。审核中的工单不可重复提交。若团队在审核过程中主动撤回整份工单，之后补充材料重新提交应关联原工单作为父工单，并沿用“已完成初审、进入管理员复核”的流程；这属于已完成初审后的补充，不是重新开始一轮全新的初审。超管将已通过工单打回后，提交人修改材料重新提交同样属于原审核链路的补充提交。
- **初审**：按当前配置在派发时生成并持久化个人截止时间；实际分配先按“历史接单总量（已完成数+待办数）→当前待办数”排序，同级候选随机打散，且有待办阈值过滤及全量兜底，并非“待办最少 → 虚拟完成数最少 → id 最小”；优先按学工号、降级按标准化姓名排除同团队成员；候选池不足 2 人自动跳过并邮件告警（含排除明细）。已提交意见不可直接覆盖，必须先撤回；撤回后重新进入待办，重提不会重复计数。
- **终审**：独占派发 1 名管理员；工单使用派发时持久化的截止时间，之后修改全局超时配置不会追溯改变已有工单；超时后自动换人（原管理员降权、`total_reassign_count+1`）；同人循环阈值、全局重分配阈值和待办负载倍数均可由超管后台修改，实际值以当前配置为准；交替循环仍按“重分配≥3 且去重管理员≤2”检测，任一兜底条件满足即自动挂起待超管介入。
- **超管干预**：强制通过/驳回会同步更新唯一终审记录，并保存改判前终审记录的审计快照；普通终审的工作量回退和 `system_forced_penalty+1` 只执行一次。重新派发会重置计数器并追加 `-1` 标记；补充初审仅限 `insufficient_staff` 且未派发终审管理员的工单。所有干预记录完整前后快照审计。
- **撤回**：提交人可在终结前撤回（挂起状态禁止）；审核员可在管理员终审提交前撤回初审结论，场景 A（有效意见<2）可补时 3 小时（消耗 `delay_used` 额度），场景 B（双人已提交）不补时。撤回后的意见重新进入待办，未重提而到期则按超时处理；已进入终态或已超时的初审意见不能撤回。
- **邮件**：模板按文档 5.5 生成；任务派发邮件使用派发时实际生效的时限和持久化截止时间。失败自动重试（间隔 5 分钟，最多 3 次），仍失败仅通知超管；超管邮箱也发送失败或未配置时，前端全局红色横幅持续提示，直至超管在系统中手动标记已处理。
- **并发安全**：涉及工单的写操作 = Redis 分布式锁（`lock:submission:{id}`，TTL 30s）+ 乐观锁（`version`）+ 数据库事务行锁；其中初审提交和提交人撤回校验请求版本，Cron 使用独立分布式锁防多实例重复执行。SQLite 本地开发不提供真正的数据库行锁。

## 6. 环境变量说明

见 [.env.example](./.env.example)。关键项：`SECRET_KEY`（务必修改）、`DATABASE_URL`、`REDIS_URL`、`SMTP_*`、`UPLOAD_DIR`、`MAX_FILE_SIZE_MB`（默认 50MB）、`TIMEOUT_HOURS`（默认 72）、`CYCLE_THRESHOLD`/`GLOBAL_REASSIGN_THRESHOLD`（默认 3/5，亦可在超管后台修改）。超时配置在工单或审核任务派发时计算并持久化：修改配置只影响之后新建或重新派发的任务，已有终审继续使用原截止时间；新派发邮件显示本次实际时限及截止时间。

### 6.1 邮件服务配置（SMTP）

系统所有通知（任务指派、审核结果、超管告警）均通过 SMTP 发送。**若未配置，邮件将全部发送失败**：邮件日志标记为 `failed`（原因“SMTP_HOST 为空”），Cron 每 5 分钟自动重试，仍失败后仅向超管告警；若超管邮箱同样不可达，则前端出现红色横幅，且超管后台概览页会显示“邮件服务未配置”黄色提示。

请**单独为系统申请一个发信邮箱**（任选其一），并在服务器 `.env` 中配置：

| 邮箱类型 | SMTP_HOST | SMTP_PORT | 说明 |
| :--- | :--- | :--- | :--- |
| QQ 邮箱 | `smtp.qq.com` | `465` | 在 QQ 邮箱“设置→账号→开启 SMTP”后获取 16 位**授权码**作为密码 |
| 163 邮箱 | `smtp.163.com` | `465` | 开启“SMTP 服务”后获取**授权码** |
| 企业微信/腾讯企业邮箱 | `smtp.exmail.qq.com` | `465` | 管理员在后台开通 SMTP，使用账号密码或授权码 |
| 阿里云/腾讯云邮件推送 | 参考云厂商文档 | `465`/`587` | 注意默认云服务器 25 端口可能被封，务必使用 465(SSL) |

```dotenv
SMTP_HOST=smtp.qq.com
SMTP_PORT=465
SMTP_USER=your_account@qq.com
SMTP_PASSWORD=你的授权码（非登录密码）
SMTP_USE_SSL=true
MAIL_FROM=your_account@qq.com
```

配置完成后重启服务：`docker compose up -d --build`。可在超管端“邮件日志”页查看发送状态与失败原因。

## 7. 生产部署建议

- 使用 `docker compose up -d --build` 部署到阿里云/腾讯云，安全组开放 `8000` 端口（或前置 Nginx 反代 + HTTPS）。
- 持久化卷：`pgdata`（数据库）、`uploads`（附件）。上传目录按清理后的团队名称加 `team_id` 分目录隔离，文件名格式为 `round{n}_{原始文件名}`。
- 单机单实例即可满足本类项目规模；如需多实例，Redis 锁 + Cron 锁已保证不冲突。
- 迁移：开发期 `auto_create_tables=True` 自动建表；如需 Alembic 管理：`cd backend && alembic revision --autogenerate -m init && alembic upgrade head`。

## 8. 使用边界与实现说明

1. **平台使用边界**：本项目针对某一特定事件的一次性审核任务开发，不以长期运行或同一团队反复提交为目标。每个团队原则上只提交本轮材料一次；后续开展新的特定事件时，应先重置数据库，再重新启动服务。
2. **团队主动撤回后的补充提交**：团队在初审流程中主动撤回整份工单，通常表示团队自行发现材料问题并准备补充。之后再次提交会关联原工单作为父工单；由于原工单已经完成初审流程，补充提交进入管理员复核流程，不重新分配双人初审。这是一次性审核任务中的补充材料流程，并非长期多轮提交能力。
3. **提交人撤回时释放审核任务计数**：文档 5.1.3 仅列明回退已提交意见者的 `total_completed_count`；为保证分配算法公平，实现中会释放“已分配但尚未提交、未超时、未撤回”的初审员 `current_pending_count`。若审核员先撤回已提交的初审意见，系统会回退其完成数并恢复一个待办；随后重新提交、超时或团队撤回时再分别完成结算，避免待办或完成数重复计算。
4. **强制终结允许对已终结工单改判**：文档“管理员已提交终审”回退分支（完成数-1、惩罚+1）在“管理员提交后工单已终结”的场景下同样适用，故 `force_finalize` 亦接受 `passed/rejected` 状态，用于超管纠错改判。
5. **分配算法与早期排序描述不同**：当前实现先进行待办负载阈值过滤，再按“历史接单总量（`total_completed_count + current_pending_count`）→当前待办数”排序，同级候选随机选择，并在候选池为空时全量兜底；超时和强制处罚通过虚拟负载影响后续分配。
